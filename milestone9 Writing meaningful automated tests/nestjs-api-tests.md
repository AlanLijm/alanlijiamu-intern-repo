# Milestone 9.8 — Using Jest & Supertest for API Testing in NestJS

## Reflection

**How does Supertest help test API endpoints?**

Supertest lets test code actually send an HTTP request to the endpoints a Nest application exposes, instead of calling a controller or service method directly like a unit test would. It provides a chainable API — `request(app.getHttpServer()).get('/cats')`, `.post('/cats').send(dto)`, `.delete('/cats/1').set('Authorization', ...)` — to simulate the kinds of requests a real client would make: HTTP method, path, request body, and headers. After sending the request, it also provides assertion methods like `.expect(200)` and `.expect(mockCats)` to check the response status code and body directly. Because the request genuinely goes into the Nest application, the whole processing pipeline actually runs — route matching, guards, the global `ValidationPipe`, the controller, the service — which is what makes it possible to verify that an entire API endpoint behaves correctly end to end, rather than just verifying one isolated piece of logic.

**What is the difference between unit tests and API tests?**

A unit test calls a method directly (e.g. `controller.findOne(1)`, `service.remove(1)`) with everything that method depends on mocked out, focusing only on whether that one method's own logic is correct — steps like guard authentication or request validation never run at all, since there's no actual request being sent. An API test (the integration test written in this milestone) sends a real HTTP request through Supertest instead, so it exercises the whole request-handling chain: routing, guards (`JwtAuthGuard`/`RolesGuard`), the global `ValidationPipe`, the controller, and the service. This gives much broader coverage — it verifies that all these pieces work correctly together as a complete API endpoint, not just one isolated piece of code. (The tests here still mock the repository rather than using a real database, so strictly speaking they're integration tests — controller, guards, and pipes are integrated, but the database isn't; a full e2e test would also use a real database and a real network call.)

**Why should authentication be mocked in integration tests?**

Without mocking, `JwtAuthGuard` would try to verify the JWT in the request against Auth0's real JWKS endpoint over the network — which means the test would either depend on a real, unstable network connection (which the test environment might not even have), or it would need a genuinely valid, unexpired JWT signed by Auth0, which is impractical to produce reliably in an automated test, let alone simulate a "user without permission" scenario with. Mocking authentication removes this dependency on an external service entirely, and lets the test directly decide who the request should be treated as — a user with the right permission for one test, a user without it for another — so both scenarios can be reproduced quickly and consistently, without results being affected by an external service's availability or network conditions.

**How can you structure API tests to cover both success and failure cases?**

For each endpoint, the approach is to think through every point where a request could be turned away or where it could succeed all the way through, and write a separate test for each: the happy path (valid request, sufficient permission — request processed normally, e.g. `GET /cats` returning the array, `POST /cats` with a valid body returning 201, `DELETE /cats/1` with the right permission returning 200); an invalid request (e.g. `POST /cats` with a missing/invalid field, caught by the global `ValidationPipe` and returning 400 — this doesn't even need the repository mocked, since the request never reaches the controller); and insufficient authorization (e.g. `DELETE /cats/1` with a user lacking the required permission, caught by `RolesGuard` and returning 403 — also not needing the repository mocked, since the request is stopped at the guard). In short: follow every gate a request passes through (validation, authentication/authorization, business logic) and ask how each one could fail, writing a test for each failure mode as well as for the fully successful path.
